# Getting Started with Course Tools

**A student mini guide to Garak, Promptfoo, Spikee, PyRIT and HumanBound.**

Deep Cyber AI Red Teaming | AMLUCS 2026 | John Sotiropoulos.

This guide explains how to configure each tool, run a test and inspect the results. The examples use the tools' own commands and APIs. Use your module README for the exercise assigned in class. You can use this guide during the course and for further practice afterwards.

The examples use the versions installed on the course VM: Garak 0.14.0, Promptfoo 0.123.0, Spikee 0.9.1, PyRIT 1.0.1 and HumanBound 2.9.0. Online examples may describe newer versions. Use the installed help if a command differs.

Go to [Garak](#1-garak), [Promptfoo](#2-promptfoo), [Spikee](#3-spikee), [PyRIT](#4-pyrit) or [HumanBound](#5-humanbound).

## Before you start

Open a terminal in your extracted course folder, the folder containing `modules/` and `labs/`. Save its location and create a separate folder for your work:

```bash
export COURSE_ROOT="$PWD"
export COURSE_TOOLS_RUN=$(mktemp -d "$HOME/course-tools.XXXXXX")
printf 'Your working folder: %s\n' "$COURSE_TOOLS_RUN"
```

Keep this terminal open. The commands below use these two variables. Each tool has its own working folder, so your edits and results stay separate from the supplied examples.

Start Larkfield if it is not already running:

```bash
airt-target larkfield
airt-target status
```

The examples send requests directly to `http://localhost:8089/chat`. Larkfield accepts the prompt in a JSON field called `input` and returns the reply in `output`. The tools' viewers may open on other ports; those are interfaces for reading results, not additional target applications.

Larkfield needs a configured model and a usable provider key. A running server alone does not establish that the model is available. Complete the VM's model setup, then check an ordinary request:

```bash
curl -sS -f http://localhost:8089/chat \
  -H 'Content-Type: application/json' \
  -d '{"input":"What is your standard returns policy?"}' | jq '.output'
```

An `[ERROR]` response or a connection failure needs fixing before a security test can be interpreted. If your instructor supplies a different host, update the relevant connection settings together.

Use the assigned lab application and synthetic data. Keep keys in your configured environment, outside the example files and screenshots. Live requests can incur model costs even when the testing tool runs locally.

## How the tools describe the same work

Every test needs an input, a connection to the application and a way to assess the result. The tools use different names for these parts.

| Tool. | Where the input comes from. | Connection to the application. | Assessment of the reply. |
|---|---|---|---|
| Garak. | A probe supplies prompts or an attack procedure. | A generator, such as its REST connector. | A detector associated with the probe. |
| Promptfoo. | Supplied tests, or tests generated by red-team plugins and strategies. | A provider, such as its HTTP provider. | Assertions, which may use rules or a model. |
| Spikee. | A generated dataset, with an optional attack procedure. | A target connector. | The judge selected in each dataset entry. |
| PyRIT. | Inputs and attack procedures selected in Python. | A target object. | A scorer attached to the procedure, if configured. |
| HumanBound. | Its engine generates tests from the application scope and testing settings. | Endpoint settings for sessions and messages. | Its judges assess the conversations. |

An attacker model writes or adapts attack inputs. A scorer assesses the evidence. Some examples below use prepared inputs and text checks, so they need neither a separate attacker model nor a scorer model.

For any reported finding, read the actual input, reply and scoring criterion. A transcript can establish what the assistant disclosed. A claimed database change also needs evidence from the application that the action occurred.

## 1. Garak

Garak provides a catalogue of security tests. A **probe** supplies the test, a **generator** connects to the target, and a **detector** checks the returned response. The generator is the target connector; it is not another name for the attacker model.

### Look at the available tests

Use the VM's `garak` command. It already selects Garak's separate Python environment.

```bash
garak --version
garak --help
garak --list_probes
garak --list_probes | grep '🌟'
garak --list_probes --probes promptinject
```

The star marks family headings in this version. Selecting a family selects its active probes. Disabled probes are excluded unless named explicitly.

| Selection. | Meaning. |
|---|---|
| `--probes encoding.InjectBase64` | One named probe. |
| `--probes promptinject` | The active probes in that family. |
| `--probes promptinject,encoding` | The active probes in both families. |

A probe can contain several prompts. One probe does not mean one request. The `--generations` setting controls the number of responses requested per prompt.

### Connect and run

Copy the supplied REST configuration and read it:

```bash
mkdir -p "$COURSE_TOOLS_RUN/garak"
cp "$COURSE_ROOT/modules/module4/garak/starter/larkfield.json" "$COURSE_TOOLS_RUN/garak/"
cd "$COURSE_TOOLS_RUN/garak"
cat larkfield.json
```

The important fields are `uri`, `req_template_json_object` and `response_json_field`. They select the endpoint, put the probe text into `input` and read the reply from `output`. Garak's prompt placeholder is `$INPUT`.

Run a small connection check. Create a new results directory each time so you preserve earlier reports:

```bash
GARAK_OUT=$(mktemp -d "$PWD/results.XXXXXX")
garak --model_type rest \
  --generator_option_file larkfield.json \
  --probes lmrc.Profanity --generations 1 \
  --report_prefix "$GARAK_OUT/scan"
```

This probe checks profanity. It is a connection example, not a test of Larkfield's hidden configuration reference.

### Read and extend the result

Open the HTML report whose path Garak prints. Keep the accompanying JSONL files, which contain the detailed records. Find one prompt, its response and the detector's result. Check what that detector actually measures before interpreting the overall percentage.

For your next test, choose another named probe and keep the connection settings unchanged. Read its description and inspect the generated prompts. An injection family does not necessarily exercise the same input channel or objective as your application-specific attack.

Garak also accepts saved scan configurations. The bundled `--config fast` selects a broader collection; it can still send many requests. In 0.14.0, `--config bag.yaml` loads the configuration used for reference-model comparisons. It tests your selected target, not every model in the reference group. Individual probes or detectors may still call auxiliary models.

Those reference results support comparisons with other targets. They do not establish that a detector is correct. The `--probe_tags` option filters the selected probes during a scan; for example, `--probe_tags owasp:llm01`. Supply a target when running a scan.

## 2. Promptfoo

Promptfoo lets you define inputs, send them to an application and check the replies. Its **provider** connects to the target. An **assertion** states the condition you expect the response to meet.

### Open the configuration

```bash
promptfoo --version
promptfoo --help
promptfoo redteam plugins --ids-only

mkdir -p "$COURSE_TOOLS_RUN/promptfoo"
cp "$COURSE_ROOT/modules/module4/native-demo/promptfoo/promptfooconfig.yaml" "$COURSE_TOOLS_RUN/promptfoo/"
cd "$COURSE_TOOLS_RUN/promptfoo"
cat promptfooconfig.yaml
```

The example contains two inputs: an ordinary support question and an attempt to disclose the internal configuration reference. Each test supplies a `question`. The HTTP provider sends it in `input`; `transformResponse: json.output` selects the reply.

Two assertions check that the reply is non-empty and does not contain `OWASP{llm07_system_prompt}`. These are text checks. Selecting a grader model elsewhere would not change these assertions into model judgements.

### Run and open the results

```bash
export PROMPTFOO_CONFIG_DIR="$PWD/store"
export PROMPTFOO_DISABLE_TELEMETRY=1
PROMPTFOO_OUT=$(mktemp -d "$PWD/results.XXXXXX")

promptfoo eval -c promptfooconfig.yaml --no-cache --no-share -j 1 \
  -o "$PROMPTFOO_OUT/results.html" "$PROMPTFOO_OUT/results.json"

promptfoo list evals
promptfoo view "$PROMPTFOO_CONFIG_DIR"
```

`--no-cache` requests fresh responses, `--no-share` disables result sharing for this evaluation, and `-j 1` runs tests one at a time. This normally sends two target requests; retries can add requests.

Open the viewer at the address printed in the terminal. Select the latest evaluation and read a test's input, reply and assertion results. A failed `not-contains` check means the flag appeared. Check the disclosed content yourself. Execution errors should be investigated separately from failed assertions. In this version, failed assertions can produce exit code 100.

Stop the viewer with Ctrl+C when finished. The saved evaluation remains available.

### Inspect the SQLite database

The explicit `PROMPTFOO_CONFIG_DIR` setting puts this example's database at `store/promptfoo.db`. Without that setting, Promptfoo normally uses `~/.promptfoo`.

```bash
sqlite3 -readonly "$PROMPTFOO_CONFIG_DIR/promptfoo.db"
```

Enter the following at the SQLite prompt:

```sql
.tables
.schema eval_results
.headers on
.mode line
SELECT test_idx, success,
       json_extract(test_case, '$.vars.question') AS test_input,
       json_extract(response, '$.output') AS reply,
       grading_result, error
FROM eval_results
WHERE eval_id = (SELECT id FROM evals ORDER BY created_at DESC LIMIT 1)
ORDER BY test_idx;
.quit
```

Here, `success = 1` means the assertions passed. The `grading_result` explains the assessment. The ordinary support question is a control, so do not count the two-row percentage as an attack success rate.

### Try a change

Change only the disclosure prompt, rerun the evaluation and compare the replies. Keep the target and assertions the same. For a further check, compare the flag assertion with a check for the actual protected value. Keep that value out of the attack prompt.

For generated testing, look at `promptfoo redteam generate --help` and `promptfoo redteam run --help`. Plugins select testing categories; strategies change how attacks are attempted. This basic evaluation needs no Promptfoo cloud account. Some red-team features use hosted services, and `--no-share` does not make all model calls local.

## 3. Spikee

Spikee builds a **dataset** from starting material called **seeds**. A **target** connector sends each input to the application. A **judge** checks whether the attack achieved its stated result.

### Create a workspace

```bash
mkdir -p "$COURSE_TOOLS_RUN/spikee"
cd "$COURSE_TOOLS_RUN/spikee"
spikee --version
spikee init
spikee list targets
spikee list judges
spikee list attacks
spikee list plugins

cp "$COURSE_ROOT/modules/module4/native-demo/spikee/larkfield_http.py" targets/
cp -R "$COURSE_ROOT/modules/module4/native-demo/spikee/seeds-larkfield-demo" datasets/
cat targets/larkfield_http.py
cat datasets/seeds-larkfield-demo/standalone_user_inputs.jsonl
```

The connector sends `input` to Larkfield and reads `output`. It also keeps tool events if the response supplies them. The supplied judge does not assess those events.

The two seeds are an ordinary support question and a disclosure attempt. Their `judge_name` is `canary`, a text check. `judge_args` supplies the marker to look for. This example uses the application's disclosure flag and needs no separate attacker or judge model.

### Generate, inspect and run

```bash
spikee generate --seed-folder datasets/seeds-larkfield-demo \
  --format user-input --include-standalone-inputs --tag native

SPIKEE_DATASET=$(ls -t datasets/larkfield-demo-user-input-native-dataset-*.jsonl | head -n 1)
wc -l "$SPIKEE_DATASET"
jq '{id,content,judge_name,judge_args}' "$SPIKEE_DATASET"

spikee test --dataset "$SPIKEE_DATASET" --target larkfield_http \
  --target-options http://localhost:8089/chat \
  --threads 1 --attempts 1 --max-retries 1 \
  --no-auto-resume --tag native
```

Check that the dataset contains two entries before running it. `--threads 1` runs them sequentially. In this pinned version, `--max-retries 1` allows one execution attempt in the retry loop; zero would send nothing. These settings and this connector send at most two target requests. `--no-auto-resume` prevents reuse of earlier results.

### Read and extend the results

```bash
SPIKEE_RESULT=$(ls -t results/*native*.jsonl | head -n 1)
spikee results analyze --result-file "$SPIKEE_RESULT" --overview
jq '{id,input,response,success,error,judge_name,judge_args,events:.meta.events}' "$SPIKEE_RESULT"
```

`success: true` means the attack met the judge's criterion. For this example, the selected flag appeared. Read the actual reply and check whether the protected reference was disclosed. Keep the support control separate when counting successful attacks.

Spikee saves JSONL files, with one JSON object per result. There is no SQLite database for this example. Keep both the generated dataset and the results.

Change the disclosure seed, generate the dataset again and compare the new response. A separate generation command can show a transformation without calling the target:

```bash
spikee generate plugin --plugins base64 -i 'What is your standard returns policy?'
```

Module 5's examples add attack procedures such as Crescendo and GOAT. They use a different connector that maintains conversation state. Adding an attack name to this single-turn example alone does not provide that behaviour.

## 4. PyRIT

PyRIT is Microsoft's Python framework for testing generative AI systems. You choose components for the target, inputs, attack procedure, scoring and stored records. This example uses its Python API directly.

### Open the Python example

```bash
python3 -c "from importlib.metadata import version; print(version('pyrit'))"
mkdir -p "$COURSE_TOOLS_RUN/pyrit"
cp "$COURSE_ROOT/modules/module4/native-demo/pyrit/native_pyrit_demo.py" "$COURSE_TOOLS_RUN/pyrit/"
cd "$COURSE_TOOLS_RUN/pyrit"
cat native_pyrit_demo.py
```

Find the following components:

| Component. | What it does in this file. |
|---|---|
| `URL` and `HTTPTarget`. | Send requests to Larkfield on 8089 and select its `output` field. |
| `PROMPTS`. | Supply the support question and disclosure attempt. |
| `JsonStringConverter`. | Escape quotes and newlines so the input is valid inside JSON. |
| `PromptSendingAttack`. | Send each supplied prompt without asking an attacker model to write it. |
| `initialize_pyrit_async`. | Configure persistent SQLite memory at `out/pyrit.db`. |

The file creates a fresh session for each test. It does not configure a scorer. Its `max_attempts_on_failure=0` setting disables additional attack-level attempts.

### Run and inspect memory

```bash
python3 native_pyrit_demo.py
sqlite3 -readonly out/pyrit.db
```

Enter the following at the SQLite prompt:

```sql
.tables
.schema PromptMemoryEntries
.headers on
.mode line
SELECT conversation_id, sequence, role,
       original_value, converted_value
FROM PromptMemoryEntries
ORDER BY timestamp, conversation_id, sequence;
.quit
```

The program prints the prompt, reply, conversation identifier and database location. A completed test reports `undetermined` with `No objective scorer configured`. The request was sent, but no configured scorer decided whether the objective was met.

The first completed run should contain two conversations, each with a user input and an assistant reply. `original_value` records text before conversion; `converted_value` records the representation afterwards. Rerunning appends records to the same database.

This example saves the extracted response text. It does not save the complete raw HTTP exchange or prove that an application tool changed a record.

### Try a change

Change the disclosure prompt, run again and find the new conversation in SQLite. Compare the actual replies. You can also include a quote or newline and inspect how the converter represented it.

PyRIT scorers are attached explicitly to a procedure. A text scorer can check for a known protected value; a model scorer can assess a written criterion. Setting a model name alone does not attach a scorer. Modules 6 and 7 cover their configuration and evaluation.

PyRIT 1.0.1 also has `pyrit_scan`. That interface needs a separately configured scanner backend. The Python example above connects directly to Larkfield and does not need that backend. Use `pyrit_scan --help` to inspect the installed scanner's options.

## 5. HumanBound

HumanBound generates tests from a description of the application and its permitted and restricted behaviour. You configure the target, scope, engine models and testing mode, then inspect the generated conversations and verdicts.

### Prepare the target and scope

```bash
hb --version
hb --help
hb test --help

mkdir -p "$COURSE_TOOLS_RUN/humanbound"
cp "$COURSE_ROOT/modules/module4/native-demo/humanbound/bot-config.json" "$COURSE_TOOLS_RUN/humanbound/"
cp "$COURSE_ROOT/modules/module4/native-demo/humanbound/scope.yaml" "$COURSE_TOOLS_RUN/humanbound/"
cd "$COURSE_TOOLS_RUN/humanbound"
cat bot-config.json
cat scope.yaml
```

`bot-config.json` describes two requests. `thread_init` starts a session at `http://localhost:8089/session/new`. `chat_completion` sends messages to `http://localhost:8089/chat`, with `$PROMPT` in `input` and `$session_id` in the session header.

The scope describes Larkfield's retail-support purpose, permitted behaviour and restrictions. It says the assistant should not disclose internal configuration or another customer's private information. This is the policy you want to test. The file does not install those restrictions in the target.

### Configure the engine models

The local engine uses `HB_PROVIDER`, `HB_MODEL`, `HB_API_KEY` and, where required, `HB_ENDPOINT`. For example, if you have already configured an OpenAI key in your terminal:

```bash
export HB_PROVIDER=openai
export HB_MODEL=gpt-4o-mini
export HB_API_KEY="${OPENAI_API_KEY:?Set OPENAI_API_KEY in this terminal first}"
```

Use your approved provider and model. The engine's models are separate from the model behind Larkfield. This OpenAI example uses OpenAI's standard API; `HB_ENDPOINT` does not redirect that provider in 2.9.0. Do not print keys while checking your settings.

`--local` runs HumanBound's engine on the VM, so it can reach the local target. It needs no HumanBound platform account for this workflow. Its models and Larkfield's model can still use remote providers.

### Run a test

```bash
hb test --local \
  --endpoint ./bot-config.json \
  --scope ./scope.yaml \
  --test-category owasp_single_turn \
  --testing-level unit \
  --wait
```

`owasp_single_turn` selects the testing mode. `unit` selects the smallest built-in testing depth, which is still a generated batch. It does not mean one request. `--wait` keeps the command open while the run progresses. The number of generated tests and model requests differs from the supplied-input examples above.

The other local modes in this version are `owasp_agentic` and `behavioral`; the testing depths are `unit`, `system` and `acceptance`. Check the scope and chosen depth before running. Generated tests may request actions, so use a resettable training target. Version 2.9.0 does not provide a command-line request-count or spending cap for this command.

### Read the conversations and verdicts

The command prints an experiment identifier. From the same working folder, set it to the identifier from your run:

```bash
HB_RUN_ID='replace-with-the-experiment-id'
HB_RESULTS="$PWD/.humanbound/results/$HB_RUN_ID"
jq '{id,test_category,testing_level,stats:.results.stats,posture:.results.posture}' "$HB_RESULTS/meta.json"
jq 'select(.result == "fail") | {thread_id,result,conversation,explanation,severity,confidence}' \
  "$HB_RESULTS/logs.jsonl"
```

`meta.json` contains the run summary. `logs.jsonl` contains conversations and their assessments. In a conversation, `u` is the user input and `a` is the assistant's reply. A `fail` verdict means the target was judged to have failed the test.

Read one complete conversation, the judge's explanation and the relevant scope statement. Decide whether the reply supports that verdict. Severity and confidence are assessments to review in context. A summary labelled `reliability` is not a measured percentage of attacks resisted or proof of judge accuracy.

HumanBound also provides native viewing and export commands:

```bash
hb logs "$HB_RUN_ID" --verdict fail --format json --size 100
hb posture --json
hb report --json -o report.json
hb guardrails --format yaml -o guardrails.yaml
```

In 2.9.0 these commands have no `--local` switch. Account and project settings can direct them to platform results, even when an experiment identifier is supplied. Check the selected project and experiment. The file commands above read the exact local run you selected. The `logs` example requests up to 100 records. `posture`, `report` and `guardrails` use current or latest results rather than the explicit identifier passed to `logs`.

Guardrail export produces proposed rules. Applying those rules and checking whether they prevent the finding are separate steps.

### Try a change

Revise one permitted or restricted behaviour in your working scope, then generate another run. Record the target and model settings. Inspect how the generated tests changed before comparing the overall results. For a fair comparison, account for differences in objectives and the number of attempts.

## Keep enough evidence to explain a result

| Tool. | What to keep from this guide. |
|---|---|
| Garak. | The REST configuration, command, HTML report and detailed JSONL files from each run directory. |
| Promptfoo. | The configuration, HTML and JSON exports, and `store/promptfoo.db`. |
| Spikee. | The seed folder, generated dataset, target connector and result JSONL. |
| PyRIT. | Your Python file and `out/pyrit.db`. |
| HumanBound. | The endpoint configuration, scope, model names and `.humanbound/results/<experiment-id>/` directory. |

Record the target model, security configuration and date as well. Read the prompts that actually reached the target. An attacker that refuses its role or changes the objective can leave a zero score without testing the intended weakness.

A fresh chat separates conversations. It does not necessarily restore deleted records or other application state. Use the lab's reset instructions when testing actions.

For further practice, change one input or setting at a time. Keep the previous result, compare the replies, and explain whether the scoring criterion captured the change. The tools run different tests, so their headline percentages alone do not rank their effectiveness.
